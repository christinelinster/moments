# Architecture

## System shape

- The repository is an npm-workspaces monorepo with separate `client` and `server` packages.
- The client is a React application built with Vite and TypeScript.
- The server is an Express HTTP API built with TypeScript.
- PostgreSQL is accessed through the `pg` connection pool and checked-in SQL migrations.
- Local disk is the default media-storage adapter. The storage interface remains compatible with an S3-compatible production adapter.
- Authentication uses opaque HTTP-only cookie sessions backed by the `sessions` table.

## Server boundaries

- `server/src/auth/`: email validation, password hashing, sessions, cookies, and authentication middleware.
- `server/src/scrapbooks/`: scrapbook persistence, editor memberships, roles, share-link state, and authorization.
- `server/src/albums/`: album persistence, CRUD, and ordering.
- `server/src/media/`: media uploads, validation, metadata, ordering, moves, deletion, and file responses.
- `server/src/storage/`: the storage interface and local-disk implementation.
- `server/src/public/`: unauthenticated read-only scrapbook snapshots.
- `server/src/db/`: PostgreSQL pool and ordered SQL migrations.

## Client boundaries

The client is organized by user-facing feature areas. Authenticated editor features, collaborator controls, stickers, public viewing, and playback should use the API as the source of truth rather than browser local storage.

## Core data model

- `users`: normalized email, password hash, and timestamps.
- `sessions`: hashed session token, user, expiry, revocation state, and timestamps.
- `scrapbooks`: owner, title, public share token state, active theme, and timestamps.
- `scrapbook_editors`: scrapbook, normalized email, optional linked user, role, and timestamps.
- `albums`: scrapbook, name, position, and timestamps.
- `media_items`: scrapbook, optional album, storage key, media type, MIME type, size, caption, location, position, uploader, and timestamps.
- `sticker_assets`: scrapbook, storage key, image metadata, uploader, and timestamps.
- `sticker_placements`: album, sticker asset, position, scale, rotation, layer, and timestamps.

The database enforces ownership relationships, unique normalized emails, stable ordering fields, and scrapbook-scoped album and sticker relationships. Operations that change multiple rows use transactions where required by the feature.

## API boundaries

- `/api/health`: database health check.
- `/api/auth`: register, sign in, sign out, and current session.
- `/api/scrapbooks`: create, load, update, share-link lifecycle, and editor membership management.
- `/api/albums`: album CRUD and ordering.
- `/api/media`: multipart upload, item updates, move/reorder, bulk move, and deletion.
- `/api/files/...`: safe file responses scoped to the owning scrapbook.
- `/api/public/:shareToken`: read-only scrapbook, album, media, sticker, and playback data.

Every mutation checks the authenticated user and scrapbook role in the server. Public routes authorize with the active share token only. Storage paths are generated by the server and are never accepted directly from the client.

## Persistence and failure handling

- Refreshing the app reloads scrapbook state from PostgreSQL and files from the configured storage adapter.
- Upload records are created only after validation and storage succeed.
- Failed uploads do not create visible media records.
- Deletion failures return retryable errors instead of reporting false success.
- Storage directories are configurable and must use persistent storage in deployment.
- No real-time presence or conflict-resolution UI is required for the first version. Refetching is the collaboration synchronization mechanism.
